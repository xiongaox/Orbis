# Orbis Git 描述

## 触发模式

- 用户输入 `git描述`：只创建本地 Git 提交，绝不执行远程操作。
- 用户输入 `git描述并提交`：创建本地 Git 提交后，执行 `git push` 推送到当前分支的上游远程仓库。
- 用户输入 `git描述并提交和同步分支`：创建本地 Git 提交后，推送 `Dev`，再将已更新的 `Dev` 合并并推送到 `main`。
- 必须优先识别最长的 `git描述并提交和同步分支`，其次是 `git描述并提交`，不得将其按较短触发词处理。

按以下步骤执行：

1. 先确认当前仓库根目录是 `Orbis`。
   - 运行 `git rev-parse --show-toplevel`。
   - 若结果路径最后一级不是 `Orbis`，立即停止并提示：此技能仅支持 Orbis 项目。

2. 收集"距离上次提交后"的改动信息。
   - 运行 `git status --short` 查看新增/修改/删除/未跟踪文件。
   - 运行 `git diff --name-status HEAD` 查看相对 `HEAD` 的文件级变更。
   - 运行 `git diff --stat HEAD` 获取改动规模与概览。
   - 若存在未跟踪文件，必须把其变更意图纳入描述。

3. 基于改动生成中文 Commit Message，保持信息准确、简洁。
   - 第一行写 Summary，使用一句话概括核心改动。
   - 第二行必须为空行。
   - 第三行开始写 Body，按要点逐行展开主要变更、重构、修复或文档更新，每行一个要点。
   - 不编造不存在的改动，不写与当前 diff 无关的内容。

4. 提交到本地 Git。
   - 运行 `git add -A`，将当前工作区全部可提交改动加入暂存区。
   - 使用生成的 Summary 和 Body 执行 `git commit`。
   - 提交成功后运行 `git rev-parse --short HEAD` 获取提交哈希。
   - 若提交失败，说明失败原因，不得声称已完成提交。

5. 仅在触发词为 `git描述并提交` 时推送 GitHub。
   - 先确认本地提交成功，再运行 `git push`，推送到当前分支已配置的上游远程仓库。
   - 不运行 `git pull`，不切换分支，不修改远程地址。
   - 若推送失败，明确说明本地提交已成功、GitHub 推送失败及失败原因。
   - 触发词为 `git描述` 时，绝不运行 `git push` 或其他远程仓库操作。

6. 仅在触发词为 `git描述并提交和同步分支` 时同步分支。
   - 此模式仅支持从 `Dev` 同步到 `main`；若当前分支不是 `Dev`，立即停止并说明原因。
   - 在开始前运行 `git fetch origin --prune`，并合并 `origin/Dev` 到本地 `Dev` 后推送 `Dev`。
   - 查找 `main` 所在 worktree。若 `main` 已被其他 worktree 占用，确认该 worktree 干净后在其中执行后续操作；若无其他 worktree 占用，则在当前 worktree 切换到 `main`。
   - 合并 `origin/main` 到本地 `main`，再合并已更新的 `Dev`，最后运行 `git push origin main`。
   - 若任一合并发生冲突，优先依据两侧改动意图解决；无法安全判断时停止并说明冲突文件。不得丢弃任一侧改动。
   - 合并或推送失败时，说明已完成的本地提交和远程推送，不得声称两分支已同步。

7. 严格遵守输出格式要求。
   - 成功时最终结果只输出一个代码块，内含 Commit Message、提交哈希，以及本次是否执行和完成 `git push` 的说明。
   - 同步分支模式还必须写明 `Dev` 和 `main` 的最终提交哈希。
   - 代码块内必须是纯文本，不使用加粗、图标、列表 markdown 标记等格式修饰。
   - Commit Message 始终满足结构：Summary / 空行 / Body。
   - 路径清洗：如果 diff 信息中包含 `file:///`、`cci://` 或本地绝对路径，必须转换为相对于项目根目录的相对路径或纯文件名。
   - 除代码块外，不额外输出解释文字。

8. 若当前没有任何可提交改动，不创建空提交。对于 `git描述` 和 `git描述并提交`，不执行推送；对于同步分支模式，仍可继续同步已有的 `Dev` 和 `main`，并在最终结果明确说明“无变更可提交，未创建本地提交”。
