# Orbis Git 描述

## 触发模式（仅三种）

| 触发词 | 本地提交 | 写入更新日志 | 推送 GitHub | 云端构建 |
|--------|:--------:|:------------:|:-----------:|:--------:|
| `git描述` | ✅ | ❌ | ❌ | ❌ |
| `git描述并提交` | ✅ | ✅ | ✅ | ❌ |
| `git描述提交并构建` | ✅ | ✅ | ✅ | ✅ |

- **必须优先识别最长的 `git描述提交并构建`**，其次是 `git描述并提交`，最后才是 `git描述`；
  不得把长触发词当作短触发词处理（这是最容易出的错）。
- `git描述并提交` 也要写更新日志：推送 GitHub 会触发**网页端（Cloudflare 正式站）**的构建与部署，
  日志若不随本次提交一起推送，线上版本就会显示旧的更新日志。**写日志必须在 `git push` 之前**。
  与 `git描述提交并构建` 的区别仅在于：不触发桌面端 / 安卓端的云端构建（不打版本标签）。
- 已废弃的 `git描述并提交和同步分支` 不再处理；若用户这么说，按最接近的现有模式执行并说明。

按以下步骤执行：

1. 先确认当前仓库根目录是 `Orbis`。
   - 运行 `git rev-parse --show-toplevel`。
   - 若结果路径最后一级不是 `Orbis`，立即停止并提示：此技能仅支持 Orbis 项目。

2. 收集"距离上次提交后"的改动信息。
   - 运行 `git status --short` 查看新增/修改/删除/未跟踪文件。
   - 运行 `git diff --name-status HEAD` 查看相对 `HEAD` 的文件级变更。
   - 运行 `git diff --stat HEAD` 获取改动规模与概览。
   - 若存在未跟踪文件，必须把其变更意图纳入描述。

3. 基于改动生成中文 Commit Message，保持信息准确、简洁。
   - 第一行写 Summary，使用一句话概括核心改动。
   - 第二行必须为空行。
   - 第三行开始写 Body，按要点逐行展开主要变更、重构、修复或文档更新，每行一个要点。
   - 不编造不存在的改动，不写与当前 diff 无关的内容。

4. 提交到本地 Git。
   - 运行 `git add -A`，将当前工作区全部可提交改动加入暂存区。
   - 使用生成的 Summary 和 Body 执行 `git commit`。
   - 提交成功后运行 `git rev-parse --short HEAD` 获取提交哈希。
   - 若提交失败，说明失败原因，不得声称已完成提交。

5. 仅在触发词包含 `并提交` / `提交并构建` 时写入更新日志。
   - **发版判断必须先问，不得默认**：触发 `git描述提交并构建` 时，先看用户是否指明了版本号
     （如「发 v2.1.2」「升到 2.1.2」）。
     - **指明版本号** → 按「发新版本」处理。
     - **未指明版本号** → **停下询问**：「本次是并入当前 v<现版本>，还是升到 v<下一版本>？」
       得到答复再继续。**绝不默认并入现版本**——默认并入会重发已发布的版本号，用户装过的设备
       收不到更新提示，且 Cloudflare 网页端与 Release 产物版本号对不上，事后要重做一遍。
     - 注意：「构建」本身不是版本号信息，只有明确说出 v 号或「发新版本/发正式版」才算指明。
   - 更新日志位置：`src/lib/appChangelog.ts` 的 `APP_CHANGELOG` 数组。
     - **并入当前最新版本**：在数组首个条目的 `items` 里补充本次要点，不新增版本条目。
     - **发新版本**：在数组头部插入新条目，并同步升级
       `src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的版本号。
       若此前已误把本次要点并入现版本条目，一并从旧条目中还原移除。
   - 日志条目用 `【新增】/【修复】/【优化】/【构建】` 前缀，面向用户描述影响，不写实现细节。
   - 涉及版本发布时同步更新根目录 `RELEASE_NOTES.md`（它是 GitHub Release 的正文，经 `body_path` 注入）。
   - **写入日志后必须补一次 `git add -A` 与 `git commit`**，确保日志本身也进入推送范围。
   - 该步骤在 `git描述并提交` 与 `git描述提交并构建` 下都要执行：两者都推 GitHub，而
     网页端正式站（Cloudflare，仅 main 分支）随推送部署，日志不更新则线上显示旧日志。
   - 触发词为 `git描述` 时不写日志。

6. 仅在触发词包含 `并提交` / `提交并构建` 时推送 GitHub。
   - **必须在第 5 步写入日志并提交之后再推送**——顺序不能颠倒，否则推上去的是不含日志的版本。
   - 运行 `git push`，推送到当前分支已配置的上游远程仓库。
   - 不运行 `git pull`，不切换分支，不修改远程地址。
   - 若推送失败，明确说明本地提交已成功、GitHub 推送失败及失败原因。
   - 触发词为 `git描述` 时，绝不运行 `git push` 或其他远程仓库操作。

7. 仅在触发词为 `git描述提交并构建` 时触发云端构建。
   - 触发方式：打标签并推送。
     ```bash
     git tag -a v<版本> -m "<版本说明>"     # 版本已发布过则先 git tag -d 与 git push origin --delete
     git push origin v<版本>                # android-build / desktop-build / ios-build 由 v* 标签触发
     ```
   - **待发标签必须等于 `src-tauri/tauri.conf.json` 里的版本号**。打标签前先核对该文件；
     若它仍是上一个已发布版本（说明第 5 步没有升版本），**停下来回到第 5 步确认是否要升版本**，
     不得直接删掉旧标签重发——重发只用于「同一版本确实要重建」的场合，且必须由用户明确要求。
   - 用 `gh run list --limit 5` 确认工作流已触发，并跟踪到结束；失败时报告失败的 job 与原因。
     `gh run watch` 偶发提前退出但 run 仍在跑，此时改用 `gh run view <id> --json status,conclusion` 复核。
   - 构建完成用 `gh release view v<版本>` 核对产物清单（文件名里的版本号应与本次标签一致），报告给用户。
   - 提示用户：**重发同一版本号时，已装该版本的设备不会收到应用内更新提示**，需手动重新下载。

8. 严格遵守输出格式要求。
   - 成功时最终结果只输出一个代码块，内含 Commit Message、提交哈希，以及本次是否执行和完成
     `git push`、是否写入更新日志、是否触发云端构建的说明。
   - 构建模式下还必须写明工作流结果与产物清单。
   - 代码块内必须是纯文本，不使用加粗、图标、列表 markdown 标记等格式修饰。
   - Commit Message 始终满足结构：Summary / 空行 / Body。
   - 路径清洗：如果 diff 信息中包含 `file:///`、`cci://` 或本地绝对路径，必须转换为相对于项目根目录的相对路径或纯文件名。
   - 除代码块外，不额外输出解释文字。

9. 若当前没有任何可提交改动，不创建空提交。
   - 对于 `git描述` 与 `git描述并提交`：不执行推送，说明"无变更可提交，未创建本地提交"。
   - 对于 `git描述提交并构建`：若本次会话已提交过、只是要触发构建，可直接进入第 7 步的构建环节，
     并在最终结果说明"无新增变更，直接执行构建"。
